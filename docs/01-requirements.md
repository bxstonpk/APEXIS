# 1. Requirements

## 1.1 ขอบเขต (Scope)

APEXIS เป็น ERP สำหรับองค์กรที่มีหลายบริษัท (multi-tenant ระดับบริษัท)

- ผู้ใช้ 1 คน (user) เป็นสมาชิกได้หลายบริษัท โดยมี role / สิทธิ์ต่างกันในแต่ละบริษัท
- ข้อมูลธุรกิจทุกชนิดผูกกับบริษัท (`company_id`) และเข้าถึงได้เฉพาะสมาชิกที่มีสิทธิ์
- ส่วนที่สร้างแล้ว:
  - **identity** — ตัวตน, การล็อกอิน, role, สิทธิ์, สมาชิกของบริษัท
  - **organization** — บริษัท (tenant) และโครงสร้างองค์กร
- เป็นฐานให้ module ถัดไป (บัญชี, จัดซื้อ, ขาย ฯลฯ)

## 1.2 ผู้ใช้งาน (Actors)

| Actor | คำอธิบาย |
|---|---|
| Guest | ยังไม่ล็อกอิน — สมัครสมาชิก / ล็อกอินได้เท่านั้น |
| User | ล็อกอินแล้ว — ดูข้อมูลตัวเอง, เปลี่ยนรหัสผ่าน, สร้างบริษัทใหม่, ดูบริษัทที่ตัวเองเป็นสมาชิก |
| Owner | ผู้สร้างบริษัท — ได้ system role `owner` ที่มีสิทธิ์ `*` (ทุกอย่าง) ในบริษัทนั้น |
| Member | สมาชิกของบริษัท — ทำได้ตามสิทธิ์ของ role ที่ได้รับ |

## 1.3 Functional Requirements — `identity`

| ID | ความต้องการ | Endpoint |
|---|---|---|
| ID-01 | สมัครสมาชิกด้วย email / ชื่อ / รหัสผ่าน (email ไม่ซ้ำ, รหัสผ่าน 8–72 ตัวอักษร) | `POST /api/v1/users` |
| ID-02 | ล็อกอินแล้วได้ JWT access token (ไม่บอกว่าผิดที่ email หรือรหัสผ่าน) | `POST /api/v1/auth/tokens` |
| ID-03 | ดูข้อมูลตัวเอง / เปลี่ยนรหัสผ่าน (ต้องยืนยันรหัสเดิม) | `GET /me`, `PUT /me/password` |
| ID-04 | ดูสิทธิ์ของตัวเองในบริษัท | `GET /companies/{id}/access` |
| ID-05 | จัดการ role: สร้าง / แก้ / ลบ / ค้นหา — system role แก้/ลบไม่ได้, role ที่มีคนใช้อยู่ลบไม่ได้ | `/companies/{id}/roles` |
| ID-06 | เพิ่มสมาชิกด้วย email พร้อมกำหนด role | `POST /companies/{id}/members` |
| ID-07 | กำหนด role ใหม่ทั้งชุด / ระงับ-เปิดใช้งานสมาชิก | `PUT .../members/{userID}/roles`, `PATCH .../members/{userID}` |
| ID-08 | ค้นหาสมาชิกตามคำค้น / สถานะ / role | `GET /companies/{id}/members` |
| ID-09 | ตั้ง owner ของบริษัทใหม่ (สร้าง role `owner` + ให้ผู้สร้างเป็นสมาชิก) | เรียกจาก organization ตอนสร้างบริษัท (ไม่มี endpoint) |

กฎธุรกิจสำคัญของ identity:

- สิทธิ์มีรูปแบบ `<resource>:<action>` รองรับ wildcard เช่น `accounting.*:read`, `identity.member:*`, `*`
- ห้ามแก้ membership ของตัวเอง (กันล็อกตัวเองออก)
- ผู้จัดการสมาชิกต้องมีสิทธิ์ครอบคลุมสิทธิ์ของเป้าหมาย และห้ามมอบสิทธิ์เกินกว่าที่ตัวเองมี (admin แก้ owner ไม่ได้)
- user ที่ถูกปิด / สมาชิกที่ถูกระงับ → ไม่มีสิทธิ์ใดๆ
- identity ไม่เก็บข้อมูลบริษัท — รู้จักแค่ `company_id`

ระบบบัญชีสินค้าไม่ได้ตั้ง = สิ้นงวด (periodic) ทุกปีบัญชี

ตัวแปรของรูปแบบเลขที่ (ORG-09 และรูปแบบของสมุดรายวัน ledger): `{prefix}`, `{yyyy}` / `{yy}` (ปี ค.ศ.), `{bbbb}` / `{bb}` (ปี พ.ศ.), `{mm}`, `{fy}` (ปีบัญชี), `{seq:N}` (เลขลำดับ N หลัก ต้องมี 1 ครั้งพอดี) — ปี / เดือนอิงวันที่ของเอกสาร; เลขที่ยาวรวมไม่เกิน 30 ตัวอักษร

รายละเอียดของบริษัท (ORG-01):

- **ประเภทธุรกิจ (`business_type`)** เลือกได้ 1 แบบตอนสร้างและแก้ไม่ได้ภายหลัง:
  `service` ธุรกิจบริการทั่วไป, `trading` ธุรกิจซื้อขายสินค้า, `manufacturing` ธุรกิจผลิตสินค้า, `construction` ธุรกิจก่อสร้าง
  - กำหนดผังบัญชีมาตรฐานที่สร้างให้ (LED-10) และค่าตั้งเริ่มต้นของขาย / จัดซื้อ / คลัง / การเงิน (ORG-10)
  - บริษัทที่มีอยู่ก่อนเพิ่มประเภทธุรกิจ = `trading` (ผังเดิมมีบัญชีสินค้าครบแล้ว)
- `POST /companies` ต้องมี `code`, `name`, `business_type` — ค่าเริ่มต้น: `base_currency` = THB, `fiscal_year_start_month` = 1, `status` = active, `legal_name_th` = `name`, `amount_decimals` = 2, `quantity_decimals` = 2
- **จำนวนทศนิยมกำหนดต่อบริษัท ไม่ fix ไว้ในโค้ด**: `amount_decimals` (จำนวนเงิน) และ `quantity_decimals` (จำนวนสินค้า) ตั้งได้ 0–6
  - ทุก module ตรวจข้อมูลที่บันทึกกับค่านี้ (ledger: จำนวนเงิน, inventory: จำนวนสินค้า / มูลค่า)
  - เพิ่มได้ แต่ลดไม่ได้ (422) — ข้อมูลเดิมที่มีทศนิยมมากกว่าจะผิดรูป
- ผู้ใช้ที่ active ทุกคนสร้างบริษัทได้
- บริษัท `inactive`:
  - อ่านข้อมูลทุกอย่างได้ตามปกติ
  - สร้าง / แก้ / ลบข้อมูลของบริษัท (สาขา, แผนก, ปีบัญชี, ปิดงวด ฯลฯ) ไม่ได้ → 422
  - ยกเว้นแก้ข้อมูลบริษัทเอง เพื่อเปิดใช้งานกลับ
  - การจัดการ role / สมาชิก (identity) ยังทำได้

กฎร่วมของ master data (ORG-02 ถึง ORG-06):

- รหัส (`code`) รูปแบบ `^[A-Z0-9][A-Z0-9_-]{0,19}$` ไม่ซ้ำในบริษัท
- ลบแบบ soft delete — ลบไม่ได้ถ้ายังมีข้อมูลอื่นอ้างถึง (409); ลบแล้วนำรหัสกลับมาใช้ใหม่ได้
- ข้อมูลที่อ้างถึง (parent, branch, department ฯลฯ) ต้องอยู่ในบริษัทเดียวกันและยังไม่ถูกลบ

## 1.4.1 Functional Requirements — `ledger` (บัญชีแยกประเภททั่วไป)

| ID | ความต้องการ | กฎธุรกิจ |
|---|---|---|
| LED-01 | **ผังบัญชี (accounts)** CRUD + ค้นหา | 5 หมวด: asset / liability / equity / revenue / expense; บัญชีคุม (`postable=false`) กับบัญชีย่อย; parent ต้องเป็นบัญชีคุมหมวดเดียวกัน ห้ามวนลูป; บัญชีที่มีบัญชีย่อยต้องเป็นบัญชีคุม; บัญชีที่ถูกใช้แล้วเปลี่ยนหมวด / เปลี่ยนเป็นบัญชีคุม / ลบไม่ได้ |
| LED-02 | **สมุดรายวัน (journals)** CRUD + ค้นหา | รหัส `^[A-Z][A-Z0-9]{0,9}$` ใช้นำหน้าเลขที่เอกสาร; มีรายการแล้วลบไม่ได้ (ปิดใช้งานแทน) |
| LED-03 | **รายการบัญชี (journal entries)** สร้าง / แก้ / ลบ draft, ค้นหา | draft ไม่ต้องสมดุล; 1–500 บรรทัด; แต่ละบรรทัดมีเดบิต *หรือ* เครดิต (> 0); บัญชีต้องเป็นบัญชีย่อย; มิติวิเคราะห์ (สาขา / แผนก / ศูนย์ต้นทุน / โครงการ) ต้องมีอยู่ในบริษัท |
| LED-04 | **ผ่านรายการ (post)** | ≥ 2 บรรทัด, เดบิต = เครดิต > 0; บัญชีและสมุดต้อง active; ต้องมีงวดบัญชีครอบคลุมวันที่และงวดต้องเปิด; ได้เลขที่ `{สมุด}{ปีบัญชี}-{000001}` เรียงไม่ขาดตอนแยกตามสมุด + ปีบัญชี; ผ่านแล้วแก้ / ลบไม่ได้ |

| LED-10 | **ผังบัญชีมาตรฐานตามประเภทธุรกิจ** | สร้างให้อัตโนมัติตอนสร้างบริษัท (ORG-10) หรือด้วย `POST /accounts/defaults` สำหรับบริษัทที่ยังไม่มีบัญชี; ฐานทุกประเภท = ผังกรมพัฒนาธุรกิจการค้า (ธุรกิจบริการ) 245 บัญชี + บัญชีเฉพาะประเภท (ตารางด้านล่าง) |

- ก่อสร้างใช้บัญชีในฐานที่มีอยู่แล้ว: งานระหว่างทำที่ยังไม่โอนให้ผู้ว่าจ้าง 1105030000, เงินรับล่วงหน้าเกินกว่างานที่ทำเสร็จ (หนี้สินที่เกิดจากสัญญา) 2103020000, เงินประกันผลงาน-เจ้าหนี้ 2103030000

- บริษัทเดิม (ซื้อขาย / ผลิต) ที่สร้างผังก่อนมีบัญชีสินค้าได้รับบัญชีสินค้าเพิ่มตอน migrate ครั้งเดียว (เฉพาะบัญชีในผังของประเภทนั้น); บริษัทบริการ / ก่อสร้างไม่ได้รับ

ข้อตกลงทางบัญชี:

- สกุลเงินเดียว (สกุลเงินหลักของบริษัท) — จำนวนเงินเป็น decimal ฐาน 10 (ไม่ใช้ float); ทศนิยมตามที่บริษัทกำหนด (`amount_decimals`)
- **ยังไม่มีการปิดบัญชีสิ้นปี**: รายได้ / ค่าใช้จ่ายเริ่มนับใหม่ที่วันเริ่มปีบัญชีของ organization; กำไร (ขาดทุน) ปีก่อนแสดงเป็นยอด "กำไรสะสมที่ยังไม่ปิดบัญชี" แยกต่างหาก
- รายการ `reversed` ยังมีผลต่อยอด (การกลับรายการคือรายการใหม่อีกใบที่หักล้างกัน)
- บริษัท inactive: อ่าน / ดูรายงานได้ แต่เขียนข้อมูลบัญชีไม่ได้ (422)

## 1.4.2 Functional Requirements — `inventory` (คลังสินค้า)

| ID | ความต้องการ | กฎธุรกิจ |
|---|---|---|
| INV-01 | **หน่วยนับ (uoms)**, **หมวดสินค้า (item-categories)** CRUD + ค้นหา | ลบไม่ได้ถ้ายังมีสินค้าใช้อยู่ |
| INV-02 | **คลัง (warehouses)** CRUD + ค้นหา | ผูกสาขาของ organization ได้ (ต้องมีอยู่จริง); มีเอกสารแล้วลบไม่ได้ |
| INV-03 | **สินค้า (items)** CRUD + ค้นหา | ชนิด stock / non_stock / service; มีการเคลื่อนไหวแล้วเปลี่ยนชนิด / หน่วยนับไม่ได้; จุดสั่งซื้อทศนิยมตามบริษัท |
| INV-04 | **เอกสารสต็อก (stock-documents)**: รับเข้า (receipt), เบิก (issue), โอนระหว่างคลัง (transfer), ปรับปรุง (adjustment) | draft → posted → cancelled; เลขที่ `GR/GI/TR/AJ{ปีบัญชี}-{000001}` เรียงไม่ขาดตอน; วันที่ต้องอยู่ในงวดที่เปิด; ใช้ได้เฉพาะสินค้าชนิด stock ที่ active และคลังที่ active |
| INV-05 | **ต้นทุน FIFO** | ขาออกตัดชั้นต้นทุนเก่าสุดก่อน (เฉพาะชั้นที่ลงวันที่ไม่เกินวันที่เอกสาร); โอนย้ายพาต้นทุน FIFO เดิมไปคลังปลายทาง |
| INV-06 | **ห้ามสต็อกติดลบ** | เบิกเกินยอดที่มี ณ วันที่เอกสาร = 422; ทำงานถูกต้องเมื่อเบิกพร้อมกันหลายคน |
| INV-07 | **ยกเลิกเอกสาร** | กลับผลที่วันที่เดิม (งวดต้องยังเปิด); เอกสารที่ของที่รับเข้าถูกใช้ไปแล้วยกเลิกไม่ได้ (ต้องยกเลิกเอกสารที่ใช้ก่อน) |
| INV-08 | **รายงาน** `stock-on-hand` (ยอดคงเหลือ + มูลค่า ณ วันที่), `stock-card` (การเคลื่อนไหวพร้อมยอดสะสม) | ผ่าน `GET /reports?book=` เดียวกับ ledger |
| INV-09 | **ระบบบัญชีสินค้า** perpetual / periodic ตั้งต่อปีบัญชี (`inventory-settings/accounting-systems/{ปี}`) | ไม่ตั้ง = periodic (สิ้นงวด — ค่าเริ่มต้น เพราะใช้กันมากกว่า); เปลี่ยนได้เฉพาะปีที่ยังไม่มีเอกสารสต็อกที่ผ่านแล้ว (ปีนั้นและปีถัดไป) |
| INV-10 | **บัญชีของสินค้า** บัญชีซื้อ / บัญชีสินค้าคงเหลือ ตั้งที่สินค้า → หมวด → ค่าเริ่มต้นของบริษัท | ใช้ตัวแรกที่ตั้งไว้; ต้องเป็นบัญชีย่อยที่ active ใน ledger |
| INV-11 | **ปรับปรุงสินค้าคงเหลือสิ้นงวด** (เฉพาะ periodic) `inventory-closings` | ปรับบัญชีสินค้าคงเหลือให้เท่ามูลค่า FIFO ณ วันสิ้นงวด ส่วนต่างลงต้นทุนขาย (ลงผ่าน ledger); งวดละครั้ง, ปิดเรียงงวด, ยกเลิก (กลับรายการ) ย้อนจากงวดล่าสุด; ปิดแล้วห้ามมีเอกสารสต็อกลงวันที่ในงวดนั้นหรือก่อนหน้า |

ข้อตกลง:
- **เอกสารสต็อกไม่ลงบัญชีเอง** — module ที่เกี่ยวข้อง (ซื้อ / ขาย) เป็นผู้ลงบัญชี โดยใช้ต้นทุนจากเอกสารสต็อก; inventory ลงบัญชีเองเฉพาะรายการปรับปรุงสิ้นงวด
- จำนวนสินค้าทศนิยมตาม `quantity_decimals`; มูลค่าปัดตาม `amount_decimals`; ต้นทุนต่อหน่วยรับได้ถึง 6 ตำแหน่ง
- การตัดชั้น FIFO บางส่วนปัดมูลค่าตามทศนิยมของเงิน; การตัดหมดชั้นใช้มูลค่าคงเหลือทั้งหมด จึงไม่มีเศษค้าง

## 1.4.3 Functional Requirements — `purchasing` (จัดซื้อ)

| ID | ความต้องการ | กฎธุรกิจ |
|---|---|---|
| PUR-01 | **ค่าตั้งจัดซื้อ** อัตรา VAT (เริ่มต้น 7%), สมุดรายวัน, บัญชี GR/IR, เจ้าหนี้, ภาษีซื้อ, ผลต่างราคา | บัญชีต้องเป็นบัญชีย่อยที่ active; อัตราใหม่มีผลกับใบสั่งซื้อที่สร้างหลังจากนี้ |
| PUR-02 | **ผู้ขาย** CRUD + ค้นหา (`vat_registered`, เลขผู้เสียภาษี 13 หลัก, เลขสาขา 5 หลัก, เครดิตเทอม) | แก้สถานะจด VAT ได้ — มีผลกับเอกสารที่สร้างหลังแก้เท่านั้น; มีใบสั่งซื้อแล้วลบไม่ได้ |
| PUR-03 | **ใบสั่งซื้อ** draft → approved → closed / cancelled | ผู้ขายจด VAT: VAT ตามอัตราที่ตั้ง เลือกราคารวม / แยก VAT ได้; ไม่จด: 0% ทุกใบ (เลือกรวม VAT = 422); **เก็บเงื่อนไข VAT + เครดิตเทอมไว้ในใบตอนสร้าง** เอกสารที่ตามมาไม่กลับไปดูผู้ขาย; อนุมัติต้องมีสิทธิ์ `approve` และได้เลขที่ `PO{ปีบัญชี}-000001` |
| PUR-04 | **ใบรับสินค้า** ตามใบสั่งซื้อ (รับบางส่วนได้) | ไม่เกินจำนวนที่เหลือ; สินค้า stock ออกใบรับเข้าคลังของ inventory (FIFO) ใน transaction เดียว; ลงบัญชี Dr สินค้าคงเหลือ (perpetual + stock) หรือบัญชีซื้อ (periodic / ไม่นับสต็อก / บริการ) / Cr GR/IR; ต้นทุนไม่รวม VAT |
| PUR-05 | **ใบแจ้งหนี้ผู้ขาย** ตามใบสั่งซื้อ | แจ้งหนี้ได้ไม่เกินจำนวนที่รับแล้ว; ราคาใบแจ้งหนี้ต่างจากใบสั่งซื้อได้ — ผลต่างลงบัญชีผลต่างราคา (perpetual + stock) หรือบัญชีซื้อ; Dr GR/IR + ภาษีซื้อ / Cr เจ้าหนี้; วันครบกำหนด = วันที่ลงบัญชี + เครดิตเทอมในใบสั่งซื้อ; เลขที่ใบแจ้งหนี้ของผู้ขายห้ามซ้ำ (ยกเว้นใบที่ยกเลิก) |
| PUR-06 | **ยกเลิก** ใบรับสินค้า / ใบแจ้งหนี้ | กลับรายการบัญชี ณ วันที่เดิม (งวดต้องเปิด); ใบรับที่แจ้งหนี้แล้วต้องยกเลิกใบแจ้งหนี้ก่อน; ของที่รับถูกใช้ไปแล้วยกเลิกไม่ได้ |
| PUR-07 | **รายงาน** `outstanding-purchase-orders` (ค้างรับ / ค้างแจ้งหนี้), `ap-aging` (อายุเจ้าหนี้ ณ วันที่ หักยอดจ่ายแล้ว), `withholding-tax` (ภาษีหัก ณ ที่จ่ายรายเดือน แยก ภ.ง.ด.3 / 53) | ผ่าน `GET /reports?book=` |
| PUR-08 | **ประเภทผู้ขายทางภาษี** บุคคลธรรมดา / นิติบุคคล (`tax_type`, บังคับ) | กำหนดแบบยื่นภาษีหัก ณ ที่จ่าย ภ.ง.ด.3 / ภ.ง.ด.53 |
| PUR-09 | **ประเภทภาษีหัก ณ ที่จ่าย** (`withholding-tax-types`) รหัส, ชื่อ, อัตรา | อัตรา > 0 ถึง 100 ทศนิยม 2 ตำแหน่ง; ใบจ่ายเก็บอัตรา ณ วันจ่าย |
| PUR-10 | **ใบจ่ายชำระ** (`supplier-payments`) ผู้ขาย 1 รายต่อใบ, ตัดหลายใบแจ้งหนี้ / จ่ายบางส่วนได้, จ่ายหลายช่องทาง (เงินสด / ธนาคารจากทะเบียน cashbank) | หักภาษีตอนจ่าย: ฐาน = ยอดก่อน VAT ตามสัดส่วนที่จ่าย; ยอดรวมช่องทางจ่าย = ยอดตัดหนี้ - ภาษีหัก; ลงบัญชีรายการเดียว Dr เจ้าหนี้ / Cr เงินสด / ธนาคาร / ภาษีหัก ณ ที่จ่ายค้างจ่าย (บัญชีตามแบบ ภ.ง.ด.); ยกเลิก = กลับรายการ ณ วันที่เดิม; ใบแจ้งหนี้ที่จ่ายแล้วยกเลิกไม่ได้ |

ข้อตกลง:
- VAT ปัดต่อบรรทัดตาม `amount_decimals`; ราคารวม VAT: VAT = ยอด × อัตรา / (100 + อัตรา)
- รับครบและแจ้งหนี้ครบทุกบรรทัด = ปิดใบสั่งซื้ออัตโนมัติ; ปิดเอง = หยุดรับ (ยังแจ้งหนี้ของที่รับแล้วได้)
- แจ้งหนี้ครบจำนวนที่รับ = ล้าง GR/IR เท่ายอดที่ลงไว้จริง (ไม่มีเศษปัดค้างใน GR/IR)
- **รายการบัญชีทุกเอกสาร: 1 ผังบัญชี = 1 บรรทัด** (รวมยอดของบรรทัดที่ลงบัญชีเดียวกัน หักกลบเดบิต / เครดิต)
- **ใบลดหนี้ผู้ขาย / ส่งคืนสินค้า** (PUR-11): อ้างอิงใบแจ้งหนี้ที่ผ่านรายการ — ส่งคืน (จำนวนไม่เกินที่ยังไม่คืน, ตัดสต็อก FIFO) หรือได้รับส่วนลด (ไม่เกินมูลค่าบรรทัด); ยอดรวมไม่เกินยอดค้าง; เลขที่ใบลดหนี้ผู้ขายห้ามซ้ำ; ยกเลิกได้ (คืนสต็อก / กลับรายการ)
- **รายงานภาษีซื้อ** (PUR-12): ตามวันที่บันทึกบัญชี เฉพาะเอกสารที่มี VAT, ใบลดหนี้ติดลบ
- ยังไม่ทำ: จ่ายล่วงหน้า, รับเงินคืนจากผู้ขาย (ลดหนี้หลังจ่ายครบ), ค่าธรรมเนียมธนาคาร, สกุลเงินต่างประเทศ

## 1.4.5 Functional Requirements — `sales` (ขาย)

| ID | ความต้องการ | กฎธุรกิจ |

| SAL-01 | **ค่าตั้งขาย**: บริษัทจด VAT หรือไม่ + อัตรา, สมุดรายวัน, บัญชีลูกหนี้ / ภาษีขาย / รายได้ค่าเริ่มต้น / ต้นทุนขาย / ภาษีถูกหัก ณ ที่จ่าย | ไม่จด VAT = 0% ทุกเอกสาร (เลือกราคารวม VAT = 422); เปลี่ยนแล้วมีผลกับเอกสารใหม่เท่านั้น |
| SAL-02 | **ลูกค้า** CRUD + ค้นหา: เลขผู้เสียภาษี, สาขา, เครดิตเทอม, `tax_type`, **วงเงินเครดิต** (ไม่ตั้ง = ไม่จำกัด) | มีเอกสารแล้วลบไม่ได้ |
| SAL-03 | **ใบเสนอราคา** draft → sent (ออกเลขที่) → accepted / rejected | เก็บเงื่อนไข VAT / เครดิตเทอมตอนสร้าง; ไม่ลงบัญชี / ไม่กระทบสต็อก; แปลงเป็นใบสั่งขายได้ครั้งเดียว เมื่อส่งแล้ว / ยอมรับ และยังไม่หมดอายุ (`valid_until`) |
| SAL-04 | **ใบสั่งขาย** draft → approved → closed / cancelled | สร้างเองหรือจากใบเสนอราคา (คัดลอกลูกค้า / บรรทัด / เงื่อนไข); อนุมัติต้องมีสิทธิ์ `approve`; **เกินวงเงินเครดิต = อนุมัติได้แต่ตอบ `warnings`** (ยอดค้าง = ลูกหนี้คงค้าง + ใบสั่งขายที่อนุมัติแล้วส่วนที่ยังไม่ออกบิล + ใบนี้) |
| SAL-05 | **ใบส่งของ** (แยกใบ) | ส่งบางส่วนได้ไม่เกินที่เหลือ; สินค้า stock ตัดสต็อก FIFO (ห้ามติดลบ) ผ่าน inventory; perpetual: Dr ต้นทุนขาย / Cr สินค้าคงเหลือ; periodic ไม่มีรายการ |
| SAL-06 | **ใบแจ้งหนี้ / ใบกำกับภาษี** — แยกใบ (ไม่เกินที่ส่งแล้ว) หรือ **รวมใบ `with_delivery`** (ส่งของ + ออกบิลในเอกสารเดียว) | Dr ลูกหนี้ / Cr รายได้ (สินค้า → หมวด → ค่าตั้ง) + Cr ภาษีขาย; รวมใบเพิ่มต้นทุนขายในรายการเดียวกัน; วันครบกำหนด = วันที่ + เครดิตเทอมในใบสั่งขาย; ส่งครบ + ออกบิลครบ = ปิดใบสั่งขายอัตโนมัติ |
| SAL-07 | **ใบเสร็จรับเงิน** ลูกค้า 1 รายต่อใบ, หลายใบแจ้งหนี้ / รับบางส่วน, หลายช่องทาง (cashbank) | ลูกค้าหัก ณ ที่จ่ายต่อบรรทัด (`wht`); รวมช่องทาง = ยอดตัดหนี้ - ถูกหัก; Dr เงินสด / ธนาคาร + ภาษีถูกหัก ณ ที่จ่าย / Cr ลูกหนี้ |
| SAL-08 | **ยกเลิก** ใบส่งของ / ใบแจ้งหนี้ / ใบเสร็จ | กลับรายการ ณ วันที่เดิม; ใบแจ้งหนี้ที่รับเงินแล้วต้องยกเลิกใบเสร็จก่อน; ใบส่งของที่ออกบิลแล้วต้องยกเลิกบิลก่อน; คืนสต็อกอัตโนมัติ |
| SAL-09 | **รายงาน** `outstanding-sales-orders`, `ar-aging` (หักยอดรับถึงวันที่), `output-vat` (ภาษีขาย), `withholding-tax-received` | ผ่าน `GET /reports?book=` |

ข้อตกลง: เลขที่ QT / SO / DO / IV / RV ตั้งรูปแบบได้ (ORG-09); ใบกำกับภาษีแยกใบและรวมใบใช้เลขชุดเดียวกัน (IV); ทุกรายการบัญชี 1 ผังบัญชี = 1 บรรทัด
SAL-10 **ใบลดหนี้ / รับคืนสินค้า** (ม.86/10): อ้างอิงใบกำกับที่ผ่านรายการ — รับคืน (สินค้า stock เข้าคลังที่ต้นทุนเดิม) หรือลดราคา; ต้องมีเหตุผล; ยอดรวมไม่เกินยอดค้าง; พิมพ์ A4 แสดงมูลค่าเดิม / ที่ถูกต้อง / ผลต่าง; รายงานภาษีขายแสดงเป็นยอดติดลบ

ยังไม่ทำ: คืนเงินลูกค้า (ลดหนี้หลังรับเงินครบ), ราคาขายตามลูกค้า, ส่วนลดท้ายบิล, สกุลเงินต่างประเทศ

## 1.6 Non-Functional Requirements

| หมวด | ความต้องการ | วิธีที่ทำ |
|---|---|---|
| API style | RESTful เท่านั้น — path เป็นคำนาม, method คือการกระทำ | ดู [04-api.md](04-api.md) |
| การค้นหา | ทุกหน้าค้นหาผ่าน URL query ของ `GET` เพื่อให้ frontend เก็บ query ไว้ใน URL — กด Back / refresh / bookmark แล้วได้ผลค้นหาเดิม | `platform/listing` |
| ความถูกต้องของข้อมูล | ทุกการเขียนอยู่ใน transaction (รวมถึงการเขียนข้าม module); DB เป็นด่านสุดท้าย (PK, FK, UNIQUE, CHECK) | ดู [02](02-architecture.md), [03](03-database.md) |
| Performance | ไม่มี N+1, ใช้ JOIN, แบ่งหน้าใน DB, เลือกเฉพาะคอลัมน์ที่ใช้, นับ total ในคิวรีเดียว (`COUNT(*) OVER()`) | repository ของแต่ละ module |
| Security | JWT, ตรวจสิทธิ์ทุก request ใน use case, parameterized query, sort ผ่าน whitelist, escape `LIKE`, ไม่ส่ง SQL/โครงสร้าง DB ให้ client, bcrypt | ดู [02](02-architecture.md) |
| Tenant isolation | ทุกคิวรีกรอง `company_id`; ข้อมูลบริษัทอื่นตอบเป็น 404/403 | integration test ครอบคลุม |
| วันที่ | รูปแบบ `YYYY-MM-DD` (ค.ศ.), เก็บเป็น `date` | `listing.ParseDate` |
